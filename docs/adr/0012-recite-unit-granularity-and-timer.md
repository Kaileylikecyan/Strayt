# ADR-0012 背诵舱按「句级对齐 + 段级分组」，进度与粒度解耦，计时器不入库

- 状态：已采纳（实现待做）
- 日期：2026-10-02
- 关联：`学习工作台产品说明文档.md` F19.1~F19.3、`app/parse/blocks.py::_flatten` /
  `split_segments`、`app/db/models.py`（`Pair` / `Piece`）、`app/jobs/engine.py`、
  `apps/web/src/pages/RecitePage.tsx`、`docs/rtm.md` 缺口 12

## 背景

用户在背诵舱实测后提了三条：原文是一段段的、背诵舱却一句一句；「中文提示」和「遮罩背诵」
行为重复；「逐句递进」没有计时。下面记录决策与理由，**不记需求讨论过程**。

## 决策

### 1. 粒度不进对齐，只进分组（`pairs.block_no`）

`pairs` 保持**句级原子**，加工时额外记下每句来自哪个版面块（`block_no`，即 PDF layout 的
`TextBlock` 序号），展示时再把同一块的对句合成一个「背诵单元」。

**为什么不把对齐本身改成段级**：`app/parse/blocks.py::split_segments` 当初选句级是刻意的，
其 docstring 记着实测数据：

```
粒度不对称会直接污染 ⑥ —— 长度平衡 DP 会认为「3 中 + 1 英」才比例正确，
  于是把 49+54 句压成 13 对，等于把三句话糊成一条。
```

样板 PDF 中文 49 句 / 英文 55 句，本就不等；段级下两侧段数同样不等，长度平衡 DP 会整篇错位。
而「对齐之后再分组」是在**已经对齐正确**的结果上做合并，没有任何错位风险 ——
这也是为什么方案必须落在这一侧。

**为什么需要 `block_no` 而不是客户端按字数拼**：用户要的是**原文的段**，
按字数拼出来的段只是「看起来像段」。版面块序号是原文结构的直接来源。

**已知代价**：`block_no` 只对新加工的资料有效。旧篇目没有该字段，按段必须**降级为按句
并在界面标注**，不能给用户一个假的段落划分。这比默默按字数拼更诚实。

### 2. 进度与粒度解耦：`last_pos` 永远记句序号

用户规则：「几句是一段，几句都背完才算整段背完，否则整段等于没背」。这条规则**完全可推导**：

```
段背完  ⟺  该段内所有 pair 的 seq 都已越过 last_pos
```

因此 `last_pos` 保持「已背到第几句」的单一语义，不引入「段序号」这第二套坐标系。
好处有三个，且互相独立：

- 切粒度不毁进度（用户可以随时按句/按段切换）；
- 旧数据零迁移（现有 25 个背诵项目的 `last_pos` 语义不变）；
- 不会出现「两套序号互相打架」——一旦并行记两套，就必然有一个迁移/回放的对齐问题。

`recited`（已背诵标记）同理可由 `last_pos` 推导，但**保留手动开关**作为覆盖手段：
用户可能整篇快速过一遍就标记「已背」，不希望系统按规则否决。

### 3. 粒度设置存设备本地，计时默认时长存服务端

两者口径不同，是刻意的：

| 设置 | 存哪 | 为什么 |
|---|---|---|
| 按句 / 按段 | 客户端本地，按篇目 id 键 | 它是**阅读偏好**不是学习数据。丢了最多重选一次；落库反而要给它加迁移、API 字段和弱同步队列条目 |
| 计时默认时长 | 服务端 settings kv | 跨设备一致性有价值 —— 电脑端背 5 分钟的习惯，网页端也该是 5 分钟 |

粒度不进弱同步队列的另一层好处：`piece_progress` 只承载学习进度，
「正在背第几段、计时到第几秒」全是纯客户端会话态。

### 4. 四档合并为三档

「中文提示（隐英文）」与「遮罩背诵（点击揭示）」的**遮蔽行为本就完全相同**，
差别只在提示语种，
拆成两档是重复。合并为「遮罩背诵」，提示语言三选一：**显示中文遮英文 / 显示英文遮中文 /
双语都遮**。第三项对应最严的自测场景（能直接用原文背的人）。

带计时的能力落在「逐句递进」，它本来就是「一次只推进一步」的模式，计时器是它的自然延伸，
不需要另开一档。

### 5. 遮罩揭示粒度跟随粒度设置

按段时一个遮罩块 = 一整段，点击整段一起揭示。与「一段是个记忆单元」保持一致；
否则会出现「段是一个整体、但遮罩是一句一格」的撕裂感。

### 6. 计时器是纯客户端会话态，不落库

时长 = 1 / 3 / 5 分钟 / 自定义，**默认值存 settings kv**，每个单元开始前可临时改
（改动不写回全局，避免「背第 7 段时试了个 8 分钟」污染之后所有段的默认值）。

计时状态本身**不落库**。理由：它是「当前这一秒在干什么」，不是学习进度；
落库只会带来「刷新页面后要不要恢复计时」这类没人需要的复杂度。
**只有揭示完成才推进 `last_pos`** —— 计时中/揭示中都还没背完。

状态机：

```
遮蔽态 --点「开始背诵」--> 计时中 --到时自动揭示 | 点「完成背诵」--> 已揭示
计时中 <-点「取消」- 遮蔽态
已揭示 --点「再来一遍」--> 遮蔽态（时长可再调，等价于重新「开始背诵」）
已揭示 --点「背诵下一部分」--> 下一单元遮蔽态（**不自动计时**，须再点「开始背诵」）
```

「下一单元不自动计时」是用户明确要求的：自动接着计时等于剥夺了每段之间调整节奏的机会。

## 后果

- 要加**一个**迁移：`pairs.block_no`（可空）。存量篇目 `block_no` 全为 NULL，
  即「按段 = 按句」。
- 篇目粒度字段**不加** —— 存客户端本地（见决策 3）。
- 旧篇目要看到真段落必须**重跑加工任务**（用户已知并同意，因为要消耗 LLM 额度）。
- 篇目列表的进度显示从 `last_pos/pair_count`（句）变成按当前粒度算的
  `已背单元/总单元`，两套口径共用一个 `last_pos`。
- `RecitePage` 的模式枚举从 4 个变 3 个，快捷键 `1/2/3` 语义随之变化。
- 计时器是纯前端逻辑，**不受弱同步约束**（同步只承载 `piece_progress`）。
- 导出快照需带上 `block_no`，否则异地恢复后段落划分丢失（会静默降级为按句）。
