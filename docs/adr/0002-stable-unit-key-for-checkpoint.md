# ADR-0002 加工单元用稳定 key，不用标题做身份

- 状态：已采纳
- 日期：2026-09-27
- 关联：`app/jobs/engine.py`（`Unit.key`、`_key_of_title`、`_migrate_done`、`_backfill_failed_keys`）

## 背景

后台任务要能断点续跑：崩了、关了窗、用户点了取消，重开之后得知道"哪几篇做完了、哪几篇
还要做"。这个"哪几篇"的标识写进 `checkpoint_json`，是续跑的全部依据。

## 决策

单元身份用 `"{index:04d}:{title}"`（`Unit.key`），**不用**裸标题。

同时提供两条迁移路径给已有 checkpoint：
- `_migrate_done` —— 旧的 `done` 只存了标题，按标题回填 key
- `_backfill_failed_keys` —— 旧的失败明细只有 `unit`（标题），回填 key；顺带剔除
  那些"后来已经做成功了"的失败记录

## 理由

**为什么不用标题。** 标题不唯一。样板里就有 `豫园·范文（一）` / `豫园·范文（二）`，
而真实材料里同名篇目（同一模板的多次练习）非常普遍。用标题当身份，两篇会被当成一篇，
续跑时漏做或重复做。

**为什么不用纯 index。** `index` 只是 `to_pieces()` 这一轮的切分顺序。切分规则
（③结构识别）一改，index 就全错位 —— 上一轮的 `done=[0..9]` 在新一轮会指向完全不同的
篇目。带上标题后，改规则时至少能看出"这一篇变了"，而不是静默地错配。

**为什么不用 hash。** 标题变了（错别字、页眉污染）就换了身份，同样错位。而
`index:title` 变了至少是可读的。

**旧数据怎么迁。** 只在**唯一匹配**时回填（`_key_of_title` 命中 1 个才返回）。
认不出来宁可保留旧格式、让那一篇重做，也不猜 —— 猜错的后果是把失败记到别的篇目头上，
界面上会看到"上海概况失败"而实际是另一篇坏了。宁可多花一次调用的钱，不可报错账。

## 后果

- key 会随标题变。标题变了的那一篇会被重做，这是**正确**的：内容变了就该重新对齐。
- `failed_units_json` 里每条现在都带 `key`，客户端可以直接把它关联到 `units_json` 的
  某一行做"重跑这一篇"（F11 要求的单章重跑）。
- 踩过的坑：`_absorb` 早期写的是 `old.get("key", old.get("unit")) == unit.key`，
  看起来兼容了旧格式，实际拿 `"豫园·范文（一）"` 去比 `"0003:豫园·范文（一）"` 永远
  不相等 —— 于是**每续跑一次就多一条一模一样的失败红字**。已由
  `test_should_backfill_failed_key_and_dedupe` 钉住。
