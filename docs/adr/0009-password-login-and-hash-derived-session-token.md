# ADR-0009：访问口令登录 + 会话令牌由口令哈希派生签名

日期：2026-09-30
状态：已采纳（取代原「访问令牌」方案）

## 背景与起因

一期按产品文档做的是**访问令牌**登录：服务端 `gen_token` 生成 256-bit 随机串，
存 PBKDF2 派生值，客户端手动粘贴。单机自用，够用。

实际用起来有两个问题：

1. **体验反了。** 要求用户「去终端执行一条命令，复制一段 40 位随机串，粘贴进一个
   叫『访问令牌』的输入框」—— 这是把服务端的运维动作推给了本该只管学习的用户。
   口令是自己脑子里本来就有的东西，令牌是凭空多出来要保管的第二个秘密。
2. **首屏必然失败且无法自助。** 令牌明文只打印一次。忘了、或换机器，就必须回到
   服务端终端。桌面端（Tauri）场景下尤其突兀：应用起来了，却要用户切到另一个
   程序去取一段凭证。

用户明确要求改成口令：**没有可用口令就要求创建，否则要求输入；口令可更改。**

## 决策

### 1. 口令哈希换 Argon2id，PBKDF2 弃用

原方案的 PBKDF2 是**故意的**，代码注释里写着理由：「输入是 256-bit 全随机值而非
人选口令，无字典攻击面」。这个理由本身是对的，但它**依赖输入是随机的**这一前提。

换成口令后前提消失：人选口令熵低，PBKDF2-HMAC-SHA256 在 GPU 上每秒可做数十亿次，
对着字典表毫无抵抗。所以换 **Argon2id**（内存硬，19 MiB / 2 轮，单次校验 40~60 ms）。

> 这条记下来是因为**同一个「不引入 argon2」的注释还会再骗人一次** ——
> 只要输入还是人选的，那条推理就不成立。

同时**移除了 pepper**（`STRAYT_ACCESS_TOKEN_PEPPER` 配置项一并删掉）。理由：
pepper 只在「攻击者拿到 DB 但拿不到应用配置」时有边际收益，而这里两者同机；
代价却是一个「pepper 文件丢了 = 口令永久无法验证」的额外故障点。Argon2id 自带
随机盐，不需要它。

### 2. 登录换会话令牌，签名密钥由口令哈希派生

不采用「每次请求都带口令」，也不用服务端随机串存会话表，而是发一个
**HMAC-SHA256 签名的令牌**：

```
key    = SHA-256("strayt-session-v1" ‖ password_hash)     ← 密钥来自 DB 那一行
payload = base64url(expires_at_unix)
token   = base64url(payload) "." base64url(HMAC(key, payload))
```

即「<过期时间戳>.<签名>」，无服务端状态。这一条同时满足四个要求：

| 要求 | 怎么满足的 |
|---|---|
| 不需要会话表 | 令牌自包含，验签是纯函数 |
| 不需要过期清理任务 | 过期时间在令牌里，验签时比 |
| 改口令 = 所有旧会话失效 | 哈希变了 → 密钥变了 → 旧签名全对不上。**这正是要的行为** |
| 服务重启不掉线 | 密钥来自 DB，不在进程内存里 |

考虑过但否掉的：

- **服务端随机串 + `sessions` 表**：多一张表、多一套过期清理、还要处理并发写。
  「改口令即全体失效」要额外写全表清空。签名方案零成本拿到这个性质。
- **Cookie 会话**：要处理 `SameSite` / `Domain` / WebView2 与 `tauri://localhost`
  的 cookie 行为差异。单机单用户，HMAC 头更省事。
- **HTTP Basic**：等于每次请求都送口令，且 Tauri WebView 里 Basic 弹框体验差。

有效期 **30 天**（`SESSION_TTL_SECONDS`）：单用户自用，一个月重输一次可接受。
过期或改口令后客户端回到 Setup 页重登即可。

### 3. 改口令要鉴权，创建口令不要

`POST /auth/setup` **免鉴权**，但**只在口令从未设置过时可用**（已设置返回 409，
不给静默覆盖留口子）。它只往 `settings` 写一行哈希，不碰任何业务数据。

`POST /auth/password` **要鉴权**（挂在 `router2` 上带 `AuthDep`），且必须验旧口令。

免鉴权的 setup 是这条链路上唯一的「无凭证写操作」。判断依据：它是**一次性初始化**，
此时按定义还不存在任何已认证主体（单用户系统没有「第一个管理员」问题）。
服务端默认只监听回环，所以这不是实际攻击面。真要暴露到局域网，应先用
`set_password` 在服务端建好口令。

### 4. 口令哈希不进导出快照 —— 这是换口令引入的**新风险**

F24 导出快照原本**包含** `settings` 全表，docstring 的理由是「存的是令牌哈希，
不泄露明文凭据」。**这个理由对令牌成立、对口令不成立**：Argon2id 哈希是离线爆破的
直接靶子，而 F24 的产物恰恰是用户会下载、可能丢进网盘或微信传出去的文件。

`export.py::REDACTED_SETTINGS` 剔除 `access_password_hash`。恢复时重新设一次口令即可，
无实际损失。

> 「哈希不是明文所以导出无害」这个推理的错误在于它只看了可逆性，没看**离线攻击价值**。
> 全随机值的摘要没价值，人选口令的摘要是靶子。

### 5. 忘记口令 = 只能用 CLI

服务端没有任何后门 —— HTTP 侧的改口令接口本身就要求先登录。逃生口是
`uv run python -m app.scripts.set_password --reset`（口令从 TTY 读，不走命令行参数，
免得进 shell history 与进程列表）。

这是必要设计而非可选：把准入换成「自己选的口令」，就必然有「忘密码」这种状态。

## 后果

- 客户端不再有「令牌」概念。`config.ts` 存 `{baseUrl, sessionToken}`，
  **不存口令**。Setup 页按 `/auth/state` 的 `password_set` 决定显示
  「创建口令」（带二次确认）或「输入口令」。
- `access_token_hash` 这个 settings 键不再使用，dev 库里那行已删。
- 错误码从 `token_missing` / `token_invalid` 收敛为 `unauthorized`，
  新增 `password_not_set` / `password_already_set` / `password_wrong`。
- 弱口令校验放在 **pydantic 字段校验器**（`PasswordIn`）而非 `hash_password` 里：
  在路由函数体里抛 `ValueError` 会变成 500，那是服务端错误不是客户端错误。
  `test_setup_weak_password_422` 与 `test_change_password_weak_new_rejected` 钉住这点。
- 口令强度只做**长度下限（8 位）**，不做「必须含大小写数字符号」。组合规则被证明会
  把人推向可预测的 `Password1!`。真正的防线是 Argon2id 的高成本。
- 新增依赖 `argon2-cffi`。
